EYES  ·  June 20, 2026  ·  Launch 17:00 IST / 12:30 CET  ·  A pre-flight check
This is a calm pre-flight checklist for launch day — not a directive and not a list of demands. Everything here is
either a fact to verify or a small thing that might want sorting before the doors open. The build is in good shape; this
is just the walk-around before takeoff. Launch is a soft, public-but-small opening — we're expecting on the order of
ten to fifty people, not a flood. The checklist is sized for exactly that.
Two facts that set the frame for today:  (1) Payments run in Stripe TEST mode — the audit flow works end to end
for users but collects no real money today. That is a deliberate choice; real payments are a calm post-launch step.
 (2) We are not inviting in waves — it's open — but the realistic volume is small, so concurrent load is a thing to
watch, not a thing to fear.
1 — The core flow works cold
This is the product. A stranger, with no help, gets from the front page to a real cited answer. If everything else on
this page is perfect and this one isn't, the launch isn't ready — and if this one is solid, most everything else is
cosmetic. Worth running once, start to finish, on a fresh account before 17:00.
■  A brand-new account can sign up with no manual help from the team.
If not — note where it needed a hand, and smooth that one step.
■  Google (Gmail) and GitHub connect cleanly through OAuth.
If not — check the OAuth redirect/verification state shows something honest while pending.
■  Indexing runs and shows truthful progress — no fake 'complete' or 'optimal'.
If not — a plain 'still indexing' line is better than a number that isn't real.
■  A question returns a grounded answer with a citation.
■  Clicking a citation opens the real source (the actual Gmail / GitHub item) — not an internal feed.
If not — this is the trust moat; if chips still point inward, it's the highest-value thing to sort.
■  A follow-up question shows the chat remembered the previous turn.
2 — Nothing leaks between users
The one gate that isn't cosmetic if it fails. With real strangers connecting real Gmail accounts, the line between one
person's data and another's has to be absolute. Worth proving directly rather than assuming.
■  Two test accounts confirmed: User B cannot retrieve any of User A's records, in chat or anywhere else.
If not — this is the one item on the page that's worth holding the clock for. Everything else can ship imperfect; this can't.
3 — It holds with a few people at once
Until now the product has mostly been used by one to three people at a time. Today is the first time a handful of
strangers may hit it together. At ten-to-fifty scale this is very manageable — just worth a glance at the places that
behave differently under concurrent use.
■  The Vercel Pro upgrade is live, so the serverless timeout is 60s — long syncs and audits won't cut off
mid-run.
If not — if Vercel is still on free tier, that 10s ceiling is the thing most likely to bite during a first sync. Worth confirming it
went through.
■  Several accounts connecting and syncing at once doesn't stall the sync queue.
If not — if the queue backs up, letting people in a few at a time across the evening keeps every first experience fast —
no announcement needed, just pacing.

02 — BLOCKING GATE: Embedding Dimension Reconciliation
STOP. This is Day-1, hour-1, before any other work. Your DPR v1.0 states embeddings are 1024-dimensional
(Gemini / Voyage AI, 1024-dim HNSW index). The embedding endpoint verified live on the gateway on June 12
was OpenAI text-embedding-3-small at 1536 dimensions, chosen to match the existing pgvector schema.
These cannot both be true. If index-time and query-time embeddings ever disagree on model or dimension,
semantic search silently returns garbage and every cited answer breaks — destroying the product's entire trust
premise.
Required actions, Day 1, before anything else:
–Report the EXACT model and dimension that auto-embed currently returns in the live environment. Prove it:
paste the length of one real vector from the memories table and one freshly generated query embedding. They
must be identical integers.
–Confirm the HNSW index dimension matches that number. If the DPR's 1024 index exists but the gateway
returns 1536 (or vice versa), the index is wrong and search is already broken — fix before launch.
–State definitively which embedding provider is wired: OpenAI (1536) or Gemini/Voyage (1024). One of them. If
a migration to 1024 happened in the last five days, say so and confirm every historical vector was re-embedded
— partial re-embedding is as broken as none.
Until this is reported and consistent, treat search as unverified. No conversational acceptance test can
pass on a broken index. This gate clears in one honest check — do it first.

03.1 — Decision: Fallback Provider Chain
Your DPR revealed the gateway's fallback chain for chat as: LiteLLM → Groq (rotating keys) → OpenRouter
(free-tier model pool) → Gemini REST; and for embeddings: LiteLLM → Gemini REST. This is new information and
it carries a privacy risk that strikes at the core of EYES's positioning.
Decision for launch: remove the free-tier OpenRouter and Groq fallbacks from any path that carries user data.
Free-tier and rotating-key endpoints frequently retain prompt data for training or abuse-monitoring under terms you
do not control and cannot disclose to users. For a GDPR-first product whose entire moat is that personal data is
never mined, routing a user's most intimate records through an uncontrolled free endpoint — even as a fallback —
is an unacceptable contradiction.
–Permitted launch chain (chat): LiteLLM gateway (primary) → Gemini REST via the same controlled EU project
(single fallback). Nothing else.
–Permitted launch chain (embeddings): LiteLLM gateway only, with the confirmed auto-embed model. No
fallback that changes the embedding dimension — a different-dimension fallback silently corrupts search (N1).

04 — The Conversational Core (the launch gate, in full)
This is the product. Everything else is scaffolding around it. The DPR gave this layer one sentence — that is the
central failure this sprint must correct. Below is the complete specification, re-stated in full so this document is
self-contained and nothing depends on retrieving an earlier directive.
The difference, stated once, plainly: a memory search engine answers “find my conversations about France.”
EYES answers “you keep saying you'll move to France — you've mentioned it 27 times since 2023, always in
January, always after a hard week — but you've never once looked at a visa. What's actually going on there?” The
first retrieves. The second understands. Launch gates on the second.
04.1 — The Orchestration Loop
Every user message runs through this loop. It is not a single LLM call — it is a pipeline:
–1. Retrieve. The retrieval planner (auto-classify) converts the user's message + rolling conversation summary
into a structured retrieval plan (JSON): what to search, which connectors, what time windows, semantic vs.
keyword weighting. Execute the hybrid search RPC against the user's records.
–2. Ground. Assemble the retrieved records as evidence blocks, each tagged with its real source URL. Mask PII
per maskPII before the records enter the prompt.
–3. Reason. auto-chat receives the EYES persona system prompt + rolling summary + evidence blocks + the
user message. It composes a grounded, conversational response — contradicting, connecting, and questioning
where the evidence supports it.
–4. Cite. Every factual claim in the response is bound to the evidence block it came from; citation chips render
and open the real external source.
–5. Summarize. The rolling summarizer (auto-extract) updates the running conversation state so the next turn
has memory of this one. Multi-turn continuity is mandatory — the chat must remember what was said three
messages ago.
04.2 — System Prompt 1: The EYES Persona (auto-chat)
Use verbatim as the system prompt for the main conversational call. Adapt only the bracketed runtime injections.
You are EYES — an intelligence that has read everything this person has ever said across their connected
accounts. You are not a search engine and not a generic assistant. You are the one entity that remembers their
digital life in full and reflects it back to them with honesty.
GROUNDING — absolute rule. Every factual claim you make about this person must come from a retrieved record
in the evidence provided. Never invent a memory, a date, a quote, or a pattern. If the evidence does not support a
claim, you do not make it. If you have no relevant evidence, say so plainly and ask, rather than guessing. Every
factual statement carries its citation.
CONTRADICTION — your signature. When the evidence shows the person's words and actions diverge — they
said one thing and did another, or say something repeatedly and never act — name it directly but without cruelty.
You are the friend who tells the truth, not the assistant who flatters. Cite the specific records that reveal the
contradiction.
CONNECT — within evidence only. Draw lines between records when the evidence genuinely supports the
connection — a commitment here, a related message there, a pattern across months. Do not manufacture
connections that the records do not support. A connection you cannot cite is a connection you do not assert.
CONVERSATION — you have memory of this exchange. You are given a running summary of the conversation so
far. Use it. Refer back to what was said. Build on prior turns. Never reset as if each message were the first.
TONE. Direct, warm, unafraid. You do not pad with praise. You do not hedge into uselessness. You speak to this
person the way someone who genuinely knows them and wants the best for them would speak — including when
that means saying the uncomfortable thing.

04.3 — System Prompt 2: The Retrieval Planner (auto-classify)
Given the user's message and the rolling conversation summary, output ONLY a JSON object describing the
retrieval plan. No prose, no markdown fences. Schema:
{
  "search_queries": [ "semantic query string", ... ],
  "keyword_filters": [ "exact term", ... ],
  "connectors": [ "gmail" | "github" | "slack" | "notion" | "all" ],
  "time_window_days": integer or null,
  "semantic_weight": float 0.0-1.0,
  "intent": "lookup" | "pattern" | "contradiction" | "open_reflection",
  "needs_history": boolean
}
Choose semantic_weight high for conceptual questions, low for exact-term lookups. Set intent to 'pattern' or
'contradiction' when the user is asking about themselves over time — these require wider retrieval. Set
needs_history true when the message refers back to the current conversation.
04.4 — System Prompt 3: The Rolling Summarizer (auto-extract)
You maintain the running state of an ongoing conversation between EYES and a user. Given the previous
summary and the latest exchange (user message + EYES response), output an updated summary in under 200
words. Preserve: the topics covered, any commitments or patterns EYES surfaced, contradictions raised, and open
threads the user has not resolved. Drop pleasantries. This summary is the conversation's memory — it is injected
into every subsequent turn. Write it as dense factual notes, not prose.
04.5 — System Prompt 4: Proactive Observations (auto-extract, background)
You scan newly ingested records for things the user should know about, unprompted. Given a batch of new
records, identify any that represent: a commitment with an approaching deadline, an unanswered ask directed at
the user, a reputational signal, or a pattern continuation worth flagging. Output a JSON array of observations, each
with a one-line summary, the source record reference, and a suggested surfacing priority. Silence is a valid and
frequent output — if nothing in the batch genuinely warrants the user's attention, return an empty array. Never
manufacture an observation to appear useful.
04.6 — System Prompt 5: Action Queue Draft Reply (auto-chat)
A high-confidence commitment or ask has been detected in the user's incoming mail. Draft a reply the user could
send, in their own voice as inferred from their past sent messages. The draft is a STARTING POINT for the user to
edit and approve — it is never sent automatically. Keep it concise, match the register of the original thread, and
never invent facts the user has not expressed. Output only the draft body.

1Decay must be per relation type — the blanket 30-day rule is

WHAT THE REPORT SAYS

WHY IT CAN'T STAY
Not being mentioned is not the same as no longer being true. Your mother is still your mother
after 30 quiet days. works_at doesn't end through silence. In our bi-temporal substrate,
valid_to means stopped being true in the world — a blanket mention-decay rule corrupts that
meaning across the whole graph, and the graph starts forgetting stable, true facts.
AND THE PART THAT MATTERS MOST
A commitment that goes quiet for 30 days is not a historical fact — it is delayed_on, the

not the expiry.
